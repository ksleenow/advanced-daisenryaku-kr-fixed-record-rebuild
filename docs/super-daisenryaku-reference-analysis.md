# 《슈퍼 대전략》 한글패치 참고 분석

## 조사 범위

- 공개 저장소: `evegood99/KR_PATCH_AGES/md/super-daisenryaku`
- 공개 릴리스: `super-daisenryaku-v0.8`
- 공개 README, 스크린샷, xdelta 메타데이터만 조사했다.
- 원본 ROM이나 패치 결과 ROM을 입수·배포하지 않았다.
- 본 프로젝트의 ROM, 설정, 빌드 스크립트는 변경하지 않았다.

## 결론 요약

《슈퍼 대전략》 사례는 메가드라이브 게임에서 **원래 글꼴 슬롯을 계속
덮어쓰는 방식만이 답은 아니며**, ROM 확장 영역에 새 폰트 뱅크를 놓고
원래 출력기를 그대로 이용할 수 있음을 보여준다. 그러나 다른 게임의
폰트 주소나 68K 수정 코드를 복사할 수 있다는 뜻은 아니다. 이 프로젝트에
전이할 수 있는 것은 다음 세 가지 설계 원칙이다.

1. 원래 번역 영역과 새 문장용 글꼴 영역을 분리한다.
2. 하나의 텍스트가 통과하는 모든 폰트 로더를 찾아 함께 검증한다.
3. 확장·재배치·문자열 변경을 한 번에 하지 않고 각각 독립된 PoC로 증명한다.

## 증거 수준

| 구분 | 확인한 근거 | 신뢰도 |
|---|---|---|
| 512 KiB → 1 MiB 확장 | 공개 README의 원본/결과 크기와 해시 | 높음 |
| 16x16·8x8 폰트 병행 | 공개 기술 개요와 실행 스크린샷 | 높음 |
| 폰트 참조 8곳 변경 | 공개 변경 이력 | 높음 |
| 렌더러 훅 미사용 | 공개 기술 개요 | 높음 |
| 개별 68K 주소와 새 뱅크 주소 | 소스가 공개되지 않음 | 미확인 |
| 실기 전체 경로 안정성 | v0.8이 검수 중으로 표시됨 | 제한적 |

따라서 공개 설명을 설계 참고 자료로는 사용할 수 있지만, 그 패치가 모든
동적 화면에서 검증됐다고 가정해서는 안 된다.

## 공개 자료에서 확인된 구조

- 원본은 512 KiB, 패치 결과는 1 MiB로 확장된다.
- 렌더러 훅 없이 폰트 뱅크 교체와 코드 스트림 재작성으로 한글화한다.
- 16x16 폰트는 메뉴, 헤더, 메시지에 사용한다.
- 8x8 폰트는 유닛명, 무기명, 숫자에 사용한다.
- 확장 공간으로 폰트 뱅크를 재배치하고 폰트 참조 8곳을 패치한다.
- 8x8 반각 카나 슬롯 82칸을 한글로 전환하되, 맵 이름에 필요한 영문
  소문자 슬롯은 보존한다.
- 같은 유닛명이 화면에 따라 8x8/16x16 양쪽으로 출력되는 경로를 모두
  처리했다고 기록돼 있다.

## 본 프로젝트와의 공통점

《어드밴스드 대전략》에서도 16x16과 8x8 폰트가 분리돼 있으며, 동일하거나
관련된 문자열이 초기 표시, 선택 반전, 선택 해제, 재진입 등 서로 다른
출력 경로를 통과한다. 과거 반복된 잔상·반전·다른 글꼴 회귀는 문자열 한
곳만 고치는 방식으로는 해결되지 않고, 참조 경로 전체를 확인해야 한다는
점에서 《슈퍼 대전략》의 사례와 일치한다.

본 프로젝트에서 이미 실측한 구조는 다음과 같다.

| 항목 | 《어드밴스드 대전략》 일본판 Rev. A 실측값 |
|---|---|
| ROM 크기 | 1,048,576 bytes |
| 16x16 원본 폰트 시작 | `0x03C86A` |
| 16x16 글리프 크기 | 32 bytes |
| 8x8 원본 폰트 시작 | `0x03850E` |
| 8x8 업로드 크기 | `0x548` bytes |
| 8x8 글리프 수 | 169개 (`0x00..0xA8`) |
| 검증된 안전 코드 범위 | `0x00..0xA6` |
| 사용 금지 범위 | `0xA7..0xFF` |
| 8x8 직접 참조 위치 | `0x008146`, `0x008200`, `0x0106AE` |
| 8x8 로더 진입점 | `0x0081FE`, `0x0106AC` |

`0xA7` 이상은 단순한 빈 글리프가 아니었다. 실험 ROM에서 제어 코드 또는
다중 바이트 처리와 충돌하여 표준 시나리오 진입 정지가 발생했다. 따라서
테이블에서 사용되지 않는 코드와 렌더러 전체에서 안전한 코드는 구분해야
한다.

## 그대로 가져올 수 없는 부분

- 두 게임은 폰트 주소, 글리프 수, 인코딩, 로더 코드가 다르다.
- 공개 저장소에는 빌드 소스나 폰트 참조 8곳의 주소가 없다.
- xdelta 결과나 다른 게임의 68K 패치를 직접 이식해서는 안 된다.
- 공개 패치의 글꼴 및 번역 그래픽을 자산으로 복사하지 않는다.

특히 xdelta 파일을 역으로 사용해 원본 게임 자산이나 글꼴을 추출하는 것은
이 문서의 목적이 아니다. 비교 대상 프로젝트의 폰트 이름, ROM 확장 방식,
검증 결과처럼 공개된 기술 사실만 참고한다.

## 과거 방식이 불안정했던 이유

초기 재구축에서는 화면에 보이는 문자열이나 글꼴 슬롯 하나를 고친 뒤 그
화면만 확인하는 일이 반복됐다. 메가드라이브 게임은 같은 의미의 문자열을
다음처럼 서로 다른 경로로 다시 그릴 수 있다.

- 화면 최초 진입 시 전체 창 그리기
- 커서가 들어올 때 반전 타일 그리기
- 커서가 빠질 때 원래 타일 복원
- 서브 화면에서 돌아올 때 부분 갱신
- 전투·생산·상황표 뒤 지도 복귀 시 VRAM 재업로드

어느 한 경로가 일본어 폰트 뱅크를 계속 가리키면, 최초 표시는 한글이어도
포커스가 빠질 때 일본어로 돌아온다. 반대로 업로드 길이나 VRAM 목적지를
늘리면 인접 타일과 화면 전체가 깨질 수 있다. 이것이 단순 문자열 치환과
폰트 뱅크 설계를 분리해야 하는 이유다.

## v029 이후에 적용할 수 있는 원칙

1. v029의 기존 16x16 한자음·가나 치환 영역과 8x8 가타카나 영역을
   불변 영역으로 잠근다.
2. 자연스러운 문장 번역용 글리프는 별도 확장 영역에 새 폰트 뱅크로 둔다.
3. 일본판 원본의 고정 레코드 길이, 제어 코드, 영문 표기를 유지한다.
4. 새 뱅크를 사용하는 화면의 로더·참조만 독립적으로 추적한다.
5. 각 문자열은 초기 표시, 포커스 인, 포커스 아웃, 재진입, 지도 복귀를
   모두 통과해야 승인한다.
6. 16x16과 8x8이 같은 의미를 표시하는 경우 두 경로를 한 묶음으로
   관리하되 각 뱅크의 글리프 코드는 독립적으로 기록한다.

### 잠금 대상

다음은 새 글꼴 PoC의 입력이 아니라 회귀 검사 기준이다.

- v029의 16x16 한자음·가나 치환 글리프
- v029의 8x8 가타카나 글리프 `0x49..0x9A`
- 숫자 `0x00..0x09`
- 일본판에서 원래 영문인 글리프와 문자열
- `0xEF000..0xEFFFF`의 기존 고정 레코드
- 원본 포인터, 실행 코드, VRAM 배치

PoC에서 변경을 허용한 주소 이외의 바이트가 하나라도 바뀌면 빌드를
실패시켜야 한다.

## 현재 판단

별도 폰트 뱅크 방식은 기술적으로 유력하다. 현재 일본판 Rev. A ROM은 이미
1 MiB이므로, 구현 단계에서는 2 MiB 확장안을 별도 실험 ROM에서 검증하는
것이 가장 단순하다. 다만 확장 자체보다 먼저 다음 사항을 증명해야 한다.

- 68K 주소 지정이 2 MiB 범위를 정상적으로 참조하는지
- 새 폰트 뱅크의 ROM 주소와 VRAM 업로드 크기
- 16x16/8x8 각 로더의 모든 진입점
- 기존 체크섬, 헤더 ROM 종단 주소, 실기/에뮬레이터 호환성
- v029 잠금 영역 및 원본 레코드가 바이트 단위로 불변인지

따라서 다음 구현은 전체 번역이 아니라, 별도 복사본에서 한 화면·한 문장만
새 뱅크로 출력하는 PoC가 적절하다. PoC가 실패해도 v029에는 영향이 없어야
한다.

## 권장 PoC 순서

### 1. ROM 확장만 검증

- v029를 별도 실험 파일로 복사한다.
- 1 MiB를 2 MiB로 확장하되 새 영역은 일정한 패딩 값으로 채운다.
- 메가드라이브 헤더의 ROM 종단 주소와 체크섬을 갱신한다.
- 코드·폰트·문자열은 바꾸지 않는다.
- 부팅, 데모, 표준 시나리오 진입, 저장 읽기, 지도 복귀를 확인한다.

이 단계가 실패하면 폰트 실험을 시작하지 않는다.

### 2. 폰트 데이터 복제만 검증

- 원본 16x16 또는 8x8 뱅크를 확장 영역에 바이트 그대로 복제한다.
- 아직 참조 주소는 바꾸지 않는다.
- v029와 실행 화면 및 RAM/VRAM 업로드가 동일해야 한다.

### 3. 참조 한 곳만 전환

- 정적이고 되돌아가기 쉬운 화면 하나를 선정한다.
- 그 화면이 사용하는 로더의 ROM 원본 주소만 새 복제 뱅크로 바꾼다.
- 새 글리프나 번역문은 넣지 않는다.
- 원본과 픽셀 단위로 같은지 확인한다.

### 4. 신규 글리프 한 글자 검증

- 새 뱅크의 한 슬롯만 신규 한글로 바꾼다.
- 고정 길이 레코드 한 곳에서만 그 슬롯을 참조한다.
- 최초/포커스 인/포커스 아웃/재진입/복귀를 캡처한다.

### 5. 16x16·8x8 교차 경로 검증

- 같은 명칭이 큰 창과 작은 상태창에 동시에 나오는 항목을 고른다.
- 두 폰트 뱅크가 독립적으로 올바른 글자를 표시하는지 확인한다.
- 한쪽을 수정했을 때 다른 쪽 ROM 범위가 변하지 않는지 검사한다.

## 다른 프로젝트에서 재사용할 조사 절차

1. 원본 ROM의 크기와 SHA-256을 고정한다.
2. 폰트처럼 보이는 연속 타일을 시트로 렌더링한다.
3. 글리프 크기와 코드 인덱스를 실측한다.
4. 폰트 시작 주소의 24/32비트 빅엔디언 값을 ROM 전체에서 검색한다.
5. 발견된 참조 주변의 68K 코드를 역추적한다.
6. DMA/복사 루프의 바이트 수와 VRAM 목적지를 기록한다.
7. 동일 문자열의 일반·반전·복원 경로를 각각 찾는다.
8. 원본 왕복 빌드가 바이트 단위로 동일함을 먼저 증명한다.
9. 한 화면·한 주소 범위만 허용하는 변경 명세를 만든다.
10. 정적 diff와 실행 검증을 모두 통과한 뒤에만 다음 화면으로 진행한다.

### 필수 실행 검증 행렬

| 상태 | 확인할 내용 |
|---|---|
| 초기 표시 | 글자, 좌표, 색상, 인접 타일 |
| 포커스 인 | 반전 폭, 글자, 팔레트 |
| 포커스 아웃 | 원문 회귀·잔상 여부 |
| 재진입 | 이전 VRAM 상태 의존 여부 |
| 서브 화면 왕복 | 전체·부분 재업로드 안정성 |
| 지도 복귀 | 테두리·상태창·맵 타일 손상 여부 |
| 장시간 진행 | 다음 턴·전투·생산 이후 재발 여부 |

## 자동 검증 권장사항

- 빌드 전후 크기, SHA-256, 메가드라이브 체크섬 기록
- 허용 주소 범위 밖 바이너리 diff 0바이트 강제
- 원본 숫자·영문 글리프 해시 고정
- 잠금된 v029 글꼴 범위 해시 고정
- 레코드별 바이트 길이와 종료 코드 고정
- 폰트 로더의 원본 주소, 길이, VRAM 목적지 목록화
- 승인 화면의 기준 스크린샷과 픽셀 diff 생성

스크린샷이 같다는 사실만으로 안전성을 확정하지 않는다. 잘못된 데이터가
아직 표시되지 않았거나 특정 포커스 경로가 실행되지 않았을 수 있으므로,
정적 diff와 실행 경로 검증이 함께 필요하다.

## 공개 시 포함하지 말아야 할 것

- 원본 또는 완성 ROM
- 원본에서 추출한 전체 폰트·그래픽 덤프
- 사용자 제공 사유 폰트 파일
- 세이브 데이터나 로컬 사용자 경로
- 다른 한글패치의 복원된 게임 자산

공개 저장소에는 분석 문서, 주소와 구조에 관한 사실, 자체 제작 도구,
패치 적용 전제와 해시, 저작권 자료를 포함하지 않는 차분 패치만 둔다.
